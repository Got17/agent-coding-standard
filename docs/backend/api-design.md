## API Design Rules
- Define every API with a machine-checkable contract: OpenAPI 3.1, Protocol Buffers, GraphQL schema, AsyncAPI, or an equivalent project-approved schema.
- Use stable, resource-oriented naming for REST endpoints (`/api/v1/users`, `/api/v1/orders/{order_id}`) and explicit operation names for RPC/GraphQL contracts.
- Validate all request payloads at the transport boundary and reject undeclared fields with `400 Bad Request`.
- Return all API errors with the standard 5-key envelope: `code`, `message`, `details`, `timestamp`, `request_id`.
- Version or deprecate breaking contract changes explicitly using protocol-appropriate mechanisms such as major API versions, GraphQL field deprecation, protobuf compatibility rules, or `Deprecation`/`Sunset` headers.

## Detailed Human Guide & Rationale

### 1. Contract-First Boundaries

Every production API needs a contract that can be checked by machines in CI. For HTTP APIs this is usually OpenAPI 3.1. For gRPC it is the `.proto` file. For GraphQL it is the schema. For event-driven APIs it may be AsyncAPI or an equivalent schema registry.

The implementation may be code-first or spec-first, but the result must be a reviewable contract that client teams, generated SDKs, tests, and AI agents can inspect without reading handler internals.

### 2. Resource And Operation Naming

REST endpoints should model stable resources with plural nouns and path parameters:

```text
GET /api/v1/users/{user_id}
POST /api/v1/users
GET /api/v1/orders/{order_id}/items
```

Avoid action-heavy REST paths such as `/getUser`, `/createOrder`, or `/processThing` unless the endpoint is genuinely modeling an operation that is not a resource lifecycle transition. RPC and GraphQL contracts may use operation names, but those names must still describe domain intent clearly and consistently.

### 3. Boundary Validation

Transport handlers must validate request bodies, path parameters, query parameters, headers, and file metadata before invoking domain services. Unknown request fields should be rejected, not silently ignored, so clients cannot accidentally depend on fields the server does not support and attackers cannot exploit mass-assignment paths.

Validation failures should return `400 Bad Request` with the standard error envelope and field-level details.

### 4. Standard Error Envelope

All API errors use the same flat 5-key JSON shape:

```json
{
  "code": "USER_NOT_FOUND",
  "message": "The requested user was not found.",
  "details": [],
  "timestamp": "2026-08-15T14:30:00Z",
  "request_id": "req_01HZX..."
}
```

`code` is a stable application error identifier. `message` is safe for clients to display or log. `details` contains validation or contextual error metadata. `timestamp` is an ISO-8601 timestamp generated by the server. `request_id` links the client-visible failure to logs and traces.

Do not nest the envelope under an additional `error` key. That contradicts the backend baseline and makes cross-service error handling harder.

### 5. Compatibility And Deprecation

Breaking changes must be planned explicitly. Removing fields, renaming fields, changing required/optional status, changing enum meanings, or changing authorization semantics can break clients even when the server still compiles.

Prefer additive changes first: add the new field or endpoint, deploy support for both old and new clients, migrate callers, then remove the legacy contract in a later major version or documented contract phase. Where the protocol supports it, publish deprecation metadata such as GraphQL `@deprecated`, protobuf reserved fields, or HTTP `Deprecation` and `Sunset` headers.
